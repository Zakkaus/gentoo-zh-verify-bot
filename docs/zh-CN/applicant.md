# 申请者流程

本文从 Telegram 入群申请开始，说明该申请如何进入验证、完成处理或失败。只记录进程从 Bot API 更新中能够确认的行为。

## 入口检查

**实现位置：**`internal/verify` 包；`internal/verify/service.go` 中的 `(*Service).OnJoinRequest`、`(*Service).joinGate` 和 `(*Service).tryTrustedBypass`。

`OnJoinRequest` 只处理已配置或已持久注册的受保护群组。验证已停用时，申请保持待处理，交由管理员审核。创建题目之前，程序先检查受信任群组。申请者只要是任一受信任群组的已确认成员，程序就清除该用户在目标群组中的验证失败记录并直接批准。受信任群组成员查询失败时，申请者按不受信任处理。成员身份已确认、但批准请求失败时，程序通知运维人员并进入普通验证，同时跳过失败冷却期检查。

不受信任且仍处于冷却期的申请者会被直接拒绝，不会收到新题目。拒绝调用失败时只记录日志；该次更新仍不再继续处理。待验证记录上限为全进程 2,000 条、每群 500 条。达到任一上限时，申请留给管理员处理；运维告警每十分钟最多发送一次。

同一用户重新申请同一群组时，新记录替换旧记录，并尽力删除旧群内验证消息和私聊验证消息。新记录获得完整时限，但不会恢复已用掉的内核答案次数和一次性提示。批准或封禁操作仍在执行时，新申请不会覆盖正在结束的记录。

## 已经在群内的成员

**实现位置：**`internal/verify` 包；`internal/verify/service.go` 中的 `(*Service).OnMemberJoined`、`joinedNow`、`(*Service).holdMember`、`(*Service).executeRelease` 和 `(*Service).removeMember`。

没有开启入群审批的群不会产生入群申请；即使开了审批，管理员直接拉人也会绕过审批。`OnMemberJoined` 覆盖这两种情况：它处理 `chat_member` 更新中「原本在群外的人成为普通成员」这一种变化。升为管理员、被降权、退群、解除禁言都不算加入。机器人、机器人自己、群管理员，以及已确认在受信任群组内的人都不验证；五分钟内刚被机器人放行的人也不验证，因此机器人自己批准入群申请所产生的成员更新不会被当成新到达。

群内通知会区分自己进来的成员和被他人邀请进来的成员：被邀请的仍然需要完成验证，通知里写明这一点，并指向可以直接放行的管理员按钮。验证本身没有任何差别，管理员不点击时，该成员照常验证。愿意信任本群邀请的群组可以在设置面板关闭这一项；默认开启，因为有人背书并不等同于完成验证。

`timeout_seconds`描述的是申请人在群外等待的时长，因此被禁言的成员另有更长的默认窗口十分钟：他们不像申请人那样正在等验证题，而禁言期间也不会造成影响。在设置面板中设置超时属于管理员的明确选择，对两种入口同时生效。

pending 记录自己属于哪一种入口，全部结算都据此分流。通过时，禁言模式恢复群组自身的默认权限，审批模式仍然调用 `approveChatJoinRequest`。失败时，禁言模式先封禁再立即解封，人被移出而邀请链接仍然可用；累计失败达到上限仍会按配置时长封禁。面向申请人的文案同样按入口区分：已经站在群里的人不会被告知「入群申请已被拒绝」。

管理员添加进来的成员不会因为早先的失败被移出——那等于机器人推翻添加他的人的决定——但仍然需要完成验证。其余处于失败冷却期的成员会被再次移出，而不是再出一道题：移出通知里写明还需等待多少秒，未到时间就重新加入会被再次移出，说明按节流只发一次。已经在验证中的成员保留原有的验证题——禁言会重新施加（退群会清掉它），截止时间不变，因此反复退群重进换不来更多时间。

Telegram 只能限制超级群成员。基本群里验证照常进行、失败照常踢出，但没有禁言，因此验证期间对方可以发言。禁言时长为验证超时再加一分钟，避免在超时与结算之间失效。

## 验证题发送方式

**实现位置：**`internal/verify` 包；`internal/verify/state.go` 和 `internal/verify/service.go` 中的 `(*Service).deliverPendingChallenge`、`(*Service).attemptPrivateChallenge`、`(*Service).postGroupChallenge`、`(*Service).SendDMChallenge`、`(*Service).sendQuizzes`；`internal/panel` 包；`internal/panel/panel.go` 中的 `(*Panel).OnStart`。

程序先预留待验证记录，再应用该群组的 `delivery_mode`：

- `group` 只发送群内验证消息。
- `dm` 尝试通过私聊发送必加频道提示或验证题。Telegram 明确拒绝时，程序回退到群内验证消息。
- `both` 是默认值。程序先发送群内验证消息，再尝试发送私聊提示或验证题。任一消息成功送达即视为验证题已送达。

只有申请者以前至少启动过一次此机器人时，Telegram 才允许机器人主动发送私聊。机器人不能主动发起会话或已被申请者屏蔽时，403 明确表示发送被拒绝。429 也明确表示拒绝；只要 `retry_after` 小于验证时限，处理器就按该时长等待并重试一次。其他明确的 4xx 拒绝会记录到日志。

传输中断、请求取消、5xx 或其他无法确认送达状态的错误可能发生在 Telegram 已接收消息之后。`dm` 不会在此情况下发送群内副本。`both` 保留已经发送的群内消息，也不会再发送第二条群内消息。

群内验证消息包含申请者、从发送时开始计算的完整时限、可选的必加频道说明、可用时的 `t.me/<bot>?start=verify_<groupID>` 按钮，以及管理员批准和封禁按钮。`Panel.OnStart` 将链接中的群组传给 `SendDMChallenge`，仅打开该群组的待验证请求。指定请求已处理或过期时，程序发送与过期请求相同的本地化无待处理提示。15 秒内重复打开同一群组的链接不会重复发送仍有效的题目。

已经发出的 `?start=verify` 旧链接继续采用原有行为：程序从 Go map 中选择一条有效记录执行初始频道检查，再由 `sendQuizzes` 发送全部有效题目。新的按群链接不依赖 map 顺序，也不会被其他群组的必加频道检查阻断。

待验证记录会持久保存当前群内消息和私聊消息的 ID。旧记录缺少私聊消息 ID 时，表示没有可删除的私聊消息。申请处理完成或超时时，程序会分别删除两条消息。故障恢复重新通知采用当前 `delivery_mode`；确认新的私聊验证消息送达后，程序记录其 ID，并在确认替代消息送达后删除两条旧消息。

两种发送均无法确认时，记录到期仍按程序原因导致的发送故障处理：成功拒绝入群申请后不增加验证失败次数，也不启动冷却期。任一消息确认送达后，程序开始正常的完整答题时限。

## 必加频道

**实现位置：**`internal/verify` 包；`internal/verify/service.go` 中的 `(*Service).SendDMChallenge`、`(*Service).OnChannelRecheck` 和 `(*Service).isChannelMember`。

选中的待验证群组要求加入频道、且申请者尚未加入时，DM 会在可用时显示公开或私有邀请链接，并提供重新检查按钮。回调绑定申请者 ID。其他用户点击时会收到无权操作提示；格式错误、已过期或已经处理的回调不会改变状态。重新检查成功后，程序发送该用户的全部有效题目。正确的选择题或内核题答案在最终处理前还会检查一次成员身份，因此答题后退出必加频道不能通过。

申请者成员查询失败通常按未加入处理，待验证记录保持有效。随后，程序检查机器人能否读取自己在该频道中的成员状态。机器人也无法访问频道时，程序发送限频的运维告警，并应用 `required_channel_fail_open`：默认值 `true` 表示该检查通过；`false` 表示记录继续待处理，效果与申请者尚未加入相同。严格模式不会立即拒绝，之后可由超时处理。

## 题型选择和选择题答案

**实现位置：**`internal/verify` 包；`internal/verify/kernel.go` 中的 `(*Service).pickMode`，以及 `internal/verify/service.go` 中的 `(*Service).OnAnswer`。

`kernel` 生成需要输入文本的内核题；`quiz` 随机选择一道题，并用密码学随机源打乱选项；`mixed` 为每条待验证记录随机选择前两种模式。运行时题库为空，导致 `quiz` 或 `mixed` 无法生成选择题时，`pickMode` 改用 `kernel`。随机源失败时，代码固定选择索引零。

选择题回调绑定群组、申请者、待验证 nonce 和选项。其他用户、非法选项索引、已经处理的记录或旧 nonce 都不能处理当前申请。错误选项立即进入验证失败流程。正确选项通过必加频道检查后，程序才会占用记录并批准申请。

## 内核题、无 Linux 备用题和 AI 诱捕

**实现位置：**`internal/verify` 包；`internal/verify/kernel.go` 中的 `(*Service).OnKernelAnswer`、`(*Service).gradeKernelAnswer` 和 `(*Service).declineAgent`。

内核题接受合理语境中的 Linux 内核版本，不接受任意带点数字。申请者最多有三次计数答案。第一次照抄示例、一次其他操作系统与内核混合说明，以及按规定进入无 Linux 备用流程的分支，不消耗答题次数。

申请者声明没有 Linux 时，还必须给出当前分钟证明。第一次格式错误会收到格式提示。声明有效后，该待验证记录会切换一次，改为需要输入文本且不显示答案的备用题。管理员配置的备用题优先；没有配置时使用本地化内置题库。完整答案经规范化后匹配即可通过；切换后提供真实有效的内核版本也可通过。备用题或内核题答错会消耗次数，最后一次错误会拒绝申请。

每条内核题和备用题都含有从 nonce 派生的 AI 诱捕指令。只有精确的 token 加 `model=...` 声明会触发。匹配的回复按错误答案处理，并作用于该用户同时存在且已发送提示的全部内核题。程序只统计一次自报模型，通知管理员，再分别拒绝每个受影响的申请。该统计是用户自报数据，不能证明实际使用了 AI。

## 通过、答错、超时、冷却和自动封禁

**实现位置：**`internal/verify` 包；`internal/verify/service.go` 中的 `(*Service).executeApprove`、`(*Service).executeBan` 和 `(*Service).finishDecline`；`internal/verify/state.go` 中的 `(*Service).recordVerifyFail` 和 `(*Service).verifyCooldownRemaining`。

Bot API 批准成功后，程序删除待验证记录，清除该群组和用户的旧失败次数，尽力删除已记录的群内验证消息和私聊验证消息，并增加内存中的当日批准计数。批准失败时，程序通知管理日志群组或当前群组，重新开放同一条待验证记录，并提供至少 60 秒且不计失败的重试窗口。

管理员触发“拒绝并封禁”后，程序会保留同一条待验证记录和两条验证消息，直到 Telegram 确认封禁与拒绝两项操作。程序先封禁，因此封禁失败时不会提前丢弃入群申请。任一操作失败时，程序都会在群内发送本地化结果，向管理日志群组或当前群组告警，并提供不计失败次数的重试窗口。

选择题答错、内核题或备用题最后一次答错、触发 AI 诱捕，以及在线状态下普通超时，都会先请求 Telegram 拒绝入群申请。拒绝成功后，程序才会尽力删除两条验证消息、记录失败和拒绝决定，并应用自动封禁阈值。拒绝失败时不记录失败次数；程序会保留两条消息，重新开放同一条待验证记录并提供至少 60 秒的重试时间，同时向管理日志群组或当前群组告警，并告知申请人该申请可能仍处于待处理状态。

同一群组和用户的连续失败只在六小时滚动窗口内累积。记录失败后，`verify_retry_seconds` 会阻止过早重新申请；有效值不大于零时不启用冷却。正数 `verify_max_fails` 达到阈值后，程序按群组当前封禁时长自动封禁。封禁成功会清除失败记录；封禁失败会告警并保留阈值记录，下一次失败将再次尝试。负数阈值停用自动封禁；封禁时长为零表示永久。

提示发送失败、批准失败后的重试、管理员封禁或拒绝失败后的重试、短暂重启期间已过期，以及故障恢复窗口都属于程序原因。这些记录的宽限计时结束时仍可能拒绝入群申请，但不会增加失败次数。故障期间的处理见[故障与恢复](outage-recovery.md)。

第一次因 Telegram 不可达而延期的超时会启动持久保存的 48 小时上限，故障恢复和重启不会重置该时间。达到上限后，程序每分钟尝试一次 Telegram。Telegram 确认拒绝申请后，申请者会收到本地化提示，说明验证未能完成，可以重新提交入群申请。该处理会删除两条验证消息，但不会增加失败次数、启动冷却期或封禁申请者。
